## Oprava 1: `_processing` flag nečistí při chybě v `translateBatch`

**Soubor:** `js/translation/batch.js`

**Problém:** Flag `_processing` se nastaví na `true` (řádek ~760), ale cleanup (řádky ~924–928) je v `finally` bloku OK, ale pokud `callAIWithRetry` vyhodí chybu v `try` bloku a catch ji odchytí, flagy se **neodeberou**. Hesla zůstanou zamčena.

**Řešení:**
Přidat `finally` blok nebo garantovat cleanup i v error cestě. Nejlepší přístup: zabalit celou logiku do `try/finally` a odstraňovat `_processing` vždy:

```js
// V translateBatch, PŘED hlavním try/catch:
const processingKeys = [...keys];
try {
  // ... existující kód ...
} catch(e) {
  // ... existující error handling ...
} finally {
  // Vždy odstraň _processing flag
  for (const key of processingKeys) {
    if (state.translated[key] && state.translated[key]._processing) {
      delete state.translated[key]._processing;
    }
  }
}
```

Odstranit duplikátní cleanup na konci `try` bloku (řádky 924–928), protože ho teď dělá `finally`.

## Oprava 2: Duplicitní definice funkcí — sjednocení do `utils.js`

**Soubory:** `js/translation/batch.js` a `js/translation/utils.js`

**Problém:** Následující funkce jsou definovány lokálně v `batch.js` I globálně v `utils.js`:
- `getFailedTopicsForFallback`
- `getMissingTopicsForRepair`
- `cloneTranslationTopicFields`
- `shouldReplaceTopicValue`
- `isBetterGenericTopicValue`
- `preserveBetterTopicsAfterBatch`
- `FALLBACK_TOPIC_ORDER`

`batch.js` nepoužívá ty z `utils.js`.

**Řešení:**
1. Ověřit, které verze jsou korektnější (pravděpodobně `batch.js`, protože jsou novější)
2. Přesunout všechny funkce z `batch.js` do `utils.js` (export)
3. V `batch.js` odebrat lokální definice a importovat z `utils.js`
4. Zkontrolovat `topicRepair.js`, který také importuje z `utils.js`

## Oprava 3: Duplicitní `escHtml` — sjednocení

**Soubory:** `js/utils.js` a `strong_translator_core_new.js`

**Problém:** Obě exportují `escHtml` s identickou implementací.

**Řešení:**
1. Ponechat `escHtml` jen v `js/utils.js`
2. V `strong_translator_core_new.js` odebrat export `escHtml` (nebo ho importovat z utils)
3. Zkontrolovat, kdo importuje `escHtml` z `core` vs z `utils` a sjednotit importy
4. V `main.js` import z `core` (`escHtml` se importuje z `core`, ale `core` importuje jen z `strong_prompts` – zkontrolovat zda `escHtml` skutečně z `core` někde využíváme)

## Oprava 4: Race condition v AUTO režimu

**Soubor:** `js/auto.js`

**Problém:** `stopAuto()` může nastavit `state.autoRunning = false`, ale `runAutoStep()` může již být v běhu a pokračuje, dokud `autoStepRunning` není false. Navíc `startAuto()` volá `runAutoStep()` přes `setTimeout`, takže může spustit další instanci.

**Řešení:**
1. Přidat kontrolu `state.autoRunning` na začátku `runAutoStep()`:
```js
if (!state.autoRunning) return;
```
2. Zabezpečit, aby `startAuto()` nevolal `runAutoStep()` pokud již běží:
```js
setTimeout(() => {
  if (state.autoRunning && !state.autoStepRunning) {
    runAutoStep();
  }
}, 50);
```
3. V `stopAuto()` také nastavit `state.autoStepRunning = false`:
```js
function stopAuto() {
  state.autoRunning = false;
  state.autoStepRunning = false; // ← přidáno
  // ...
}
```

## Oprava 5: Chybějící `await` v `processTopicRepairQueue`

**Soubor:** `js/translation/topicRepair.js`, řádky ~720–721

**Problém:**
```js
saveProgress();       // ← NEČEKÁ
await sleepMs(...);   // ← NEČEKÁ (chybí await!)
```

**Řešení:**
```js
await saveProgress();
await sleepMs(state.currentInterval * 1000);
```

Poznámka: `saveProgress()` musí vracet Promise. Zkontrolovat implementaci `saveProgress` v `storage.js` – pokud nevrací Promise, obalit do `async`:
```js
await (saveProgress() || Promise.resolve());
```

## Oprava 6: `parseWithOpenRouterNormalization` modifikuje globální stav

**Soubor:** `js/translation/utils.js`, `js/ai/call.js`

**Problém:** `parseWithOpenRouterNormalization(raw, keys, state.translated)` přímo modifikuje `state.translated` jako side-effect. Pokud parsing ztroskotá v půlce, částečné výsledky zůstanou v stavu a nelze je snadno zretryovat.

**Řešení:**
1. V `call.js` (řádek 412): Parsovat do lokálního objektu, nikoli přímo do `state.translated`:
```js
const parseTarget = {}; // lokální objekt
const parsed = parseWithOpenRouterNormalization(raw, keys, parseTarget);
```
2. Až je parsing úspěšný, merge výsledků do `state.translated`:
```js
Object.assign(state.translated, parseTarget);
```
3. Alternativně (méně invazivní): zachytávat výstup `parseTranslationsCore` do lokálního objektu a kontrolovat, zda všechny klíče byly parsovány, než se merge do stavu.

## Oprava 7: Token limit kontrola jen pro Groq

**Soubor:** `js/auto.js`, řádek 267

**Problém:**
```js
function isAutoTokenLimitReached() {
  const limit = getAutoTokenLimit();
  return limit > 0 && state.groqTokens.total >= limit;
}
```
Tokeny se inkrementují v `ai/call.js` jen pro token usage z response, ale `state.groqTokens` se nikde explicitně neinkrementuje — zkontrolovat jak se počítají tokeny.

**Řešení:**
1. Zkontrolovat inkrementaci tokenů — v `batch.js` (řádek 786–791) se logují tokeny, ale neinkrementují `state.groqTokens`.
2. Přidat inkrementaci tokenů pro všechny providery, nebo alespoň pro aktuálně používaný provider.
3. Upravit `isAutoTokenLimitReached()` aby používal celkový počet tokenů ze všech providerů:
```js
function isAutoTokenLimitReached() {
  const limit = getAutoTokenLimit();
  if (limit <= 0) return false;
  const total = state.totalTokens.total; // nebo suma per-provider
  return total >= limit;
}
```
